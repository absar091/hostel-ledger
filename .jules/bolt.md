## 2024-05-26 - Native Date String formatting performance overhead
**Learning:** `Date.prototype.toLocaleTimeString()` and `Date.prototype.toLocaleDateString()` are surprisingly expensive when called repeatedly in large lists or loops (e.g., in `TransactionItem` mapped lists) because they internally instantiate an `Intl.DateTimeFormat` object on every single call. A benchmark shows `toLocaleTimeString` taking ~9.8s vs `Intl.DateTimeFormat` taking ~174ms for 100k calls, a roughly 50x performance hit.
**Action:** Always cache `Intl.DateTimeFormat` instances outside of render loops or components (as module-level singletons) and use `.format(date)` instead of `.toLocaleTimeString` or `.toLocaleDateString` for formatting dates in lists, taking care to explicitly check for Invalid Date objects (`Number.isNaN(date.getTime())`) since `format()` throws while native string methods return "Invalid Date".
